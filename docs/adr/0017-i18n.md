# ADR-0017: One en-GB catalogue, read through next-intl and use-intl

- **Status:** Accepted
- **Date:** 2026-09-11
- **Deciders:** Founder (decision D7 in the approved M0 plan); Claude Code for the package layout
- **Spec sections:** §3 (GBP, en-GB, Europe/London), §9 (plain English), §16 M0

## Context

Five apps show text to people: customer-web (Next.js), merchant-portal and admin (Vite) and two Expo apps. Phase 1 has one locale, but strings scattered through components are hard to review for plain English, and expensive to extract if a second locale ever comes. D7 chose next-intl for customer-web and its core library, use-intl, for the others: one ICU message format across all five.

## Decision

1. **One package.** `@voltdrop/i18n` exports `LOCALE` (`en-GB`), `TIME_ZONE` (`Europe/London`) and the catalogue, `messages`.
2. **One catalogue, namespaced by feature**, not by app (`health.up`, later `checkout.*`, `orders.*`), so a phrase shown in several apps is written once. It's a TypeScript object, which every bundler in the monorepo (Next.js, Vite, Metro) imports the same way, and which gives each app typed message keys.
3. **Libraries.** customer-web uses next-intl: a request config returns the locale, time zone and messages, and `NextIntlClientProvider` passes them to client components. The Vite and Expo apps wrap their root in use-intl's `IntlProvider` with the same three values.
4. **Always UK time.** Every provider gets `TIME_ZONE`, so dates and times render in Europe/London whatever the device or server is set to.
5. **Tested.** A unit test formats every message through use-intl, so an ICU syntax error fails the build rather than a screen.
6. **Money stays in `@voltdrop/domain`.** Prices are integer pence formatted by the domain package (ADR-0012), never by ICU number formatting, so there is one money formatter.

## Consequences

- No hard-coded text in components. Reviews of wording happen in one file.
- Adding a locale later means a second catalogue and choosing `LOCALE` per request or device; components don't change.
- `TODO(M6)`: confirm `Intl.PluralRules` and `Intl.NumberFormat` on Hermes in both Expo apps, and add the FormatJS polyfills if either is missing. The M0 messages use neither, so the export doesn't prove it.

## Alternatives considered

- **react-intl (FormatJS) everywhere.** Also ICU, but next-intl fits the App Router's server components better, and D7 settled it.
- **i18next.** Its own message format by default, and weaker type safety for keys.
- **One catalogue per app.** Shared phrases would be translated several times and drift apart.
